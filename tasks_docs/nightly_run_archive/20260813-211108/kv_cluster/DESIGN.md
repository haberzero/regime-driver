# KV Cluster 子系统设计决策定稿

## 设计决策 A：主写备份同步复制（选型）

**chosen：主写备份同步复制（write-through）**

- 所有 set/delete 在 ReplicaManager 的单一锁内先写 primary、再写 backup，二者都成功才返回。
- backup 始终是 primary 已提交写入历史的一个完整前缀。
- 写后读一致：set() 返回后，读（主库）必见新值，且 backup 已持久化，failover 不丢任何已提交写入。

**被否方案：异步复制**

- 写主库后立即返回，backup 异步追赶 → 主库的近期写入可能尚未到达 backup。
- 不可接受点：一旦主库故障触发 failover，最近一批已对客户端确认的写入会丢失，违反“写后读一致”与“已提交写不丢失”的硬性要求；故障窗口内的语义无法向调用方保证。
- 代价说明：同步复制以写延迟换取强一致，通过把两处写入限制在内存 + 追加式 journal 控制开销。

## 设计决策 B：分片映射——简单取模（chosen）

**chosen：简单取模 `crc32(key) % shard_count`**

- crc32 对字节确定，跨进程、跨运行（不受 PYTHONHASHSEED 影响）结果一致，测试可复现。
- O(1) 直接定位到目标分片，无环查找/虚拟节点开销，实现与推理成本最低。
- 本任务分片数在构造时固定（shard_count 不可变，无扩容/缩容/重平衡需求），因此无需一致性哈希的平滑重分布能力。

**被否方案：一致性哈希**

- 增加一致性哈希环、虚拟节点、后继查找等复杂度，收益（动态增删节点时只迁移部分 key）在本任务“shard 数固定”的约束下完全用不上。
- 不可接受点：复杂度高、可测试性差，且对本场景无实际收益。

## 边界处理要点

- 并发：KVStore/ReplicaManager 各自持锁，跨分片操作互不阻塞；barrier 8 线程竞争下无数据丢失、无异常外泄。
- 恢复：set/delete 先追加 op-journal 再改内存；崩溃模拟（截断的尾部记录）恢复时跳过无法解析的半条记录，已提交写不丢。
- 隔离：mark_shard_down 后仅该分片抛 ShardDownError，其余分片正常。
- 复制失败：backup 写失败 → 回滚 primary 旧值 → 抛 ReplicationError → 集群其余分片继续可用。
