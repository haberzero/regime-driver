# 机制归属边界（内核 vs 用户特化）

> 本文明确系统里哪些是"内核（通用机制，与角色无关）"，哪些是"用户特化（角色/流程/节点自定义）"。
> 面向需要做架构决策或扩展系统的开发者。阅读前建议先看 `architecture/02_statechart_network.md`。
>   纠正两点：① 把"审查者/开发者"当内核概念的偏差；② 把本可自定义的机制写死的倾向。
> 关联：`docs/architecture/02_statechart_network.md`（最终架构）。

---

## 1. 核心认知修正（用户纠正）

### 1.1 节点 ≠ 角色
- **角色分离 = session 分离**（不同角色关注不同对话空间）
- **节点分离 = skill 注入 + 需求内容分离**（同审查者可负责不同节点）
- 同一个角色（session）负责多个节点完全合理：角色不变，节点变。

### 1.2 开发者和审查者没有本质区别
从"自定义角色、自定义流程、自定义节点"的角度：
- **内核不关心谁叫开发者、谁叫审查者**。
- 它们只是**用户特化的自定义角色实例**。
- 内核只认识抽象的：session、节点、交接、流转。

### 1.3 "防双失忆"也是策略，不是看门狗
- 有些使用者可能允许双失忆。
- "审查者流转时锁开发者"是**用户自定义策略**，**不是内核写死**。

## 2. 内核（通用机制，与角色无关，定死）

| 机制 | 说明 |
|---|---|
| session | 一个"会累的对话个体"，有生命周期（自评/交接） |
| 节点 | 一个工作单元，声明 skill 注入 + 需求内容 |
| 交接（Handoff） | session 之间的状态传递（结构化、可审计） |
| 流转 | 节点之间如何推进（状态机） |
| 安全监控 | 死循环/卡死检测 + abort（看门狗层） |
| 确定性门 | verdict/action 白名单（看门狗层） |
| 收敛检测 | 质询打转检测（看门狗层） |

## 3. 用户特化（可自定义，与角色绑定）

| 机制 | 说明 |
|---|---|
| 角色定义 | 一组 session 生命周期策略 + skill 集合 + 工作目录 |
| 节点→角色映射 | 哪个节点由哪个角色负责 |
| 流转策略 | 何时切换 session、是否允许双失忆 |
| 脑容量阈值 | 40%/70% 等 |
| 交接模板 | 正常/紧急交接文档格式 |
| 自评协议提示词 | 自评的 system prompt |

## 4. 角色注册（当前实现）

内核只认识**抽象角色 id**；`developer`/`reviewer` 是**用户注册的角色实例**（`core/role.py` 的
`RoleRegistry` + `default_roles()`）。节点通过 `role` 字段命名持有它的角色（session），
同一角色可拥有多个节点，不同角色占据不同 session。

## 5. 边界纪律

- **内核通用化**：`Actor`/`role` 接受**任意角色 id**，不写死 `developer|reviewer|machine`。
- **角色注册**：用户定义角色（策略 + skill + 目录），节点映射到角色。
- **流转策略可自定义**：session 切换、是否锁锚点，都是用户策略。
- **保留看门狗层**：安全监控、确定性门、收敛检测、节点预算。
