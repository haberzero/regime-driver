## 1. 背景与核心问题

### 1.1 workflow-regime 是什么

一套**与项目无关的智能化工作制度**，四层：
- **工作原则**（`AGENTS.md`）：自主推进偏好、上报阈值、禁 push、分支政策、破坏性重构授权、"只记录不断决"。
- **流程技能**（`skills/` 10 个）：实现、复核、质询、质量、无目的审视、文档治理、设计哲学。
- **任务控制文档**（`task-control/` 8 篇）：WORKLOG / NEXT_STEPS / PENDING_TASKS / 决策记录 / 临时任务文档 / 交接文档 的书写规范与生命周期。
- **goal 机制**（`07_goal_mechanism.md`）：**去插件化**目标生命周期（Phase A 设定 → B 推进 → C 阻塞判断 → D 完成/停止 → E 交接），落到文档上由智能体"自觉执行"。

### 1.2 核心问题（结构性缺陷）

> **把制度化执行放在被监控者的上下文里必然漂移。**

workflow-regime 的全部能力（skill、AGENTS 原则、goal 协议）都是"上下文里的指令"，依赖智能体的内存自觉。而 LLM 随上下文增长必然遗忘固定流程、遗忘自查、遗忘质询。**这不是 skill 质量问题，是结构性缺陷。**

**结论**：制度化执行必须**搬出被监控者**，由外部一个"半固定半智能"的制度机器人持有并执行。被监控者退化为纯执行终端。

## 2. 目标系统：OA 办公体系（三层架构）

```
┌──────────────────────────────────────────────────────────────┐
│  顶层人类用户（只看最终汇报 + 上报阈值项；可随时拉闸）              │
└──────────────▲───────────────────────────────────────────────┘
               │ 最终汇报 / blocked / human_escalate
┌──────────────┴───────────────────────────────────────────────┐
│  L1 制度机器人 = 固定代码（OA 系统）                            │
│   · 状态机（编译自 workflow-regime）                           │
│   · skill 资源：按节点"时机关联"选择性注入，绝不预置给任何 session │
│   · 与审查者之间只有【固定 JSON 契约】                          │
│   · 收到 ask → 发消息给开发者 → 等回复 → 喂回审查者              │
│   · 收到 advance → 执行流转代码 → 进入下一节点逻辑               │
│   · 收到 abort → 中断指定 session；收到 report_user → 上报人类   │
│   · 确定性门校验 JSON；硬规则确定性强制；维护任务控制文档          │
└──────────────┬──────────────────────────────┬─────────────────┘
       调用(注入skill+上下文)           收固定JSON
┌──────────────▼──────────────────────┐ ┌──▼──────────────────┐
│  L0 审查者（独立 opencode session）   │ │ L2 开发者 worker      │
│   · 无 skill 预置                     │ │  · 无插件/无goal/无skill│
│   · 只读：read/grep/glob/list         │ │  · miniconda+项目依赖  │
│   · 禁止 bash/edit/write              │ │  · 基础 AGENTS.md(少量 │
│   · 不可跑命令 → 经 JSON 要求开发者跑  │ │    自主度，仅项目事实)  │
│   · 推演节点/设计质询/判定             │ │  · 不自查不质询         │
│   · 全局状态自省（与机器人配合，见 §6）│ │  · 按段工作+协议汇报     │
└─────────────────────────────────────┘ └─────────────────────┘
```

**OA 隐喻**：机器人 = OA 系统（路由任务、表单=JSON 契约、审批=审查者判定、文档=任务控制文档）。人类问问题时绝不会"把 skill 丢给智能体"，而是结合进度与场景有机组织提问——这正是机器人按节点把 skill+进度+上下文组装成一次审查者调用。

### 三层不变式
1. **L1 是唯一控制者**：只有固定代码能发消息/中断/流转/改文档；LLM 永远只输出 JSON 判定，不直接操作。
2. **L0 是唯一判定者**：节点演进与质询设计只由审查者产出，经确定性门。
3. **L2 是纯执行者**：只响应指令并汇报，不持有制度能力。

## 3. 各层职责（已确认决策）

### 3.1 L1 制度机器人（固定代码）
- 状态机 `regime.json`：编译自 workflow-regime 的节点图与转移。
- 持有全部 skill；按节点选择并注入审查者调用（不预置给开发者/审查者 session）。
- 与审查者之间只有固定 JSON 契约（§4）。
- 确定性门校验；执行动作；维护任务控制文档（git 承载），给开发者下发**蒸馏后的指令**（开发者不直接管理过程文档）。
- 硬规则确定性强制（§7）：禁 push、分支政策、期限、删除纪律、5 轮会话检查。
- 会话管理（§6）。

### 3.2 L0 审查者（智能，一个独立 opencode session）
- **无 skill 预置**：每次判定由机器人注入 skill + 组装上下文（开发者工作汇报 + 当前节点 + 任务控制文档快照 + 选定的 skill）。
- **只读、不可跑命令**（read/grep/glob/list；**bash/edit/write 一律 deny**）。
- 需要验证/跑命令时，**通过 JSON 要求开发者执行**（"请运行 pytest ... 并报告"）。
- 判定输出固定 JSON；可主动请求机器人补充上下文（`request_context`）。
- **全局状态自省**：与机器人配合维护一份**开发者不可见**的工程项目状态清单，用于定期回顾 / 按任务进度提问（见 §6.3，后续单独设计）。
- 会话健康：每 5 轮对话向自己询问 session 长度、是否应更换、是否有阶段性总结（§6.2）。

### 3.3 L2 开发者 worker
- **无插件、无 goal 自动循环、无 skill**。
- 容器内环境：**python miniconda + 项目相关依赖包** + git + curl（§8）。
- **基础 `AGENTS.md`**（少量自主度）：仅项目专属事实（测试命令、目录结构、语言/命名约定）。**不给制度流程**（自查/质询/流程判断全部由审查者外部接管）。
- **不自查、不自我质询**：检查与质询由审查者有机提出。
- 按段工作，段末按协议汇报（§5.4 `[WORK_DONE]` 协议）。
- 会话健康：机器人每 5 轮询问是否达里程碑、是否应新开会话；**仅当独立任务完整完成且可复现可验证时才更新会话**；更新时交接参考 `task-control/06_handoff.md` 设计（§6.1）。
- 首版范围：**1 个开发者 session**（多 session 后续扩展）。

## 4. 判定 JSON 契约（固定格式，L1↔L0 唯一通道）

### 4.1 Schema

```json
{
  "node": "string",                      // 审查者当前所在节点标识（机器人传入，审查者原样回填）
  "verdict": "issue_resolved | issue_pending | blocked | advance | human_escalate",
  "action":   "ask_developer | request_context | advance | abort_session | report_user",
  "message_to_developer": "string|null", // action=ask_developer 时必填：发给开发者的问题/指令
  "next_state": "string|null",           // action=advance 时必填：目标节点标识
  "context_requested": "string|null",    // action=request_context 时必填：需要机器人补充的信息
  "confidence": 0.0,                     // 0..1
  "reason": "string"                     // 1-2 句依据
}
```

### 4.2 确定性门（机器人强制，与 LLM 输出无关）
| 规则 | 检查 |
|---|---|
| 字段白名单 | `verdict`/`action` 必须属于上述允许集，否则拒绝 |
| 必填联动 | `ask_developer→message_to_developer` 非空；`advance→next_state` 非空且在状态机节点集内；`request_context→context_requested` 非空 |
| 边界 | `confidence ∈ [0,1]`；低于 action 阈值（如 abort/report ≥0.7）拒绝 |
| 一致性 | `verdict` 与 `action` 匹配（如 `blocked`↔`report_user`；`advance`↔`issue_resolved/advance`） |

### 4.3 动作映射（机器人确定性执行）
| action | 机器人行为 |
|---|---|
| `ask_developer` | 把 `message_to_developer` 发给开发者 session → 等开发者按段协议汇报 → 取汇报喂回审查者重新判定 |
| `request_context` | 机器人补充 `context_requested` 所指信息（任务控制文档/状态清单/账本），重新组装调用审查者 |
| `advance` | 执行 `next_state` 的状态机流转代码 → 进入下一节点逻辑（新一轮提问/信息提供） |
| `abort_session` | 中断指定开发者 session（异常时） |
| `report_user` | 上报人类（含 `blocked` / `human_escalate` 场景，附 reason），等待人类指令 |

**提问与推进分离**：`ask_developer` 是"提问回路"（审查者↔开发者，经机器人路由），`advance` 是"推进回路"（状态机流转）。二者由 JSON 的 `action` 区分，绝不混在一条消息里。

## 5. 状态机（从 workflow-regime 编译）

### 5.1 顶层：goal 生命周期（`07_goal_mechanism`）
```
Phase A 设定 → Phase B 推进 → [Phase C 阻塞判断] → Phase D 完成/受阻/定时停 → Phase E 交接
```
- A：机器人读决策记录/人类指令，把目标写成可验收最终状态 + 子任务序列，落 NEXT_STEPS。
- B：对每个子任务走主循环（5.2）。
- C：审查者判定 `blocked` → 先 `request_context` 穷尽自主手段 → 仍 blocked → `report_user`。
- D：对照目标声明逐项验收（审查者）→ 完成/受阻/定时到达即停。
- E：写交接文档（`06_handoff`），会话更新。

### 5.2 主循环：自主工作循环（`08_autonomous_loop`）
```
理解 → 设计质询 → 自主决策 → 实现 → 自反馈验证 → 自主纠错 → 交付自查 → 收尾
```
每步是状态机的节点；"设计质询/自反馈验证/交付自查"是**审查者主导**（外部质询与检查），"实现/纠错"是**开发者主导**（机器人下发指令执行）。

### 5.3 子状态机（实现展开）
- **code-workflow**（开发者执行路径）：Phase 0 理解任务 → 1 理解代码 → 2 方案设计 → 3 实现 → 4 测试验证 → 5 收尾。审查者在 2/4 边界介入质询与验证。
- **code-review**（审查者执行路径）：独立验证 → 分类 → 严格分组 → 决策准备 → 实施后核验 → 规则永久化。
- **背景侧**：质量维护 Tier A/B/C + 无目的审视（低密度，机器人按节奏调度）。
- **文档治理**（doc-governance）：机器人触发审查者执行文档体系检查。

### 5.4 开发者段结束协议（`[WORK_DONE]`，无插件的外部约定）
- 机器人给开发者下发指令时要求：每段结束以最后一行 `[WORK_DONE]` + 结构化汇报（改动文件 / 测试命令与结果 / 技术债 / 待决点）结尾。
- 机器人读到标记即视为段结束，提取汇报喂回审查者。无插件依赖。

## 6. 会话管理机制

### 6.1 开发者 session
- **每 5 轮对话**，机器人向开发者询问：当前 session 是否达到里程碑？是否应新开会话？
- **更新原则**：仅当**独立任务完整完成且可复现可验证**时才更新会话（关闭旧、开新）。
- **交接**：更新会话前写交接文档（`06_handoff` 设计思想：状态/做了什么/下一步/原则/约束/待决/完整 goal 模板），供新会话完整接续。

### 6.2 审查者 session
- **每 5 轮对话**，机器人提示审查者自我评估：当前 session 长度如何？是否应更换？是否有阶段性总结？
- 审查者不每次新建（省 token）；上下文控制靠机器人组装每次判定 + 5 轮评估 + 必要时按评估结果更换/压缩。

### 6.3 全局状态清单（开发者不可见，后续单独设计）
- 审查者与机器人配合维护一份**开发者不可见**的工程项目状态清单（跨 session 的项目事实、决策、风险、待核验项）。
- 用途：定期回顾 / 结合任务进度提出更有机的质询；审查者自省的基础。
- 载体：git 承载的项目状态文档（机器人维护，审查者只读+经 JSON 更新），开发者不接触。
- **本项标记为单独设计**（PENDING，不阻塞 L1 骨架）。

## 7. 硬规则（L1 确定性强制，不交给 LLM 判断）

| 规则 | 内容 |
|---|---|
| 禁 push | 除非人类明确授权，禁止任何 `git push`；只本地 commit |
| 分支政策 | 大范围破坏性重构 100% 走独立分支；确认技术路线后才手动更新主开发分支；**永不触碰 `main`** |
| 期限 | 定时到达即停，不以"快完成了"超时 |
| 删除纪律 | 临时文档/会话完成并经确认后删除；禁止长期留存过程产物 |
| 上报阈值 | `blocked` / `human_escalate` 必上报人类，不自动越权 |

## 附：与 PLANNING 的关系

- 本设计是 `PLANNING.md` "上帝对话框"（M1+）的**务实落地**：L1=调度器内核、L0=交互智能面、L2=纯执行者；反循环五原则（事件总线/不阻塞/分层不可改写/有界自省/超时兜底）在本架构中以"固定代码 + JSON 契约 + 确定性门 + 会话轮换"形式体现。
- 后续若演进上帝对话框，本架构是其自然基座（OA 表单 → 事件总线；JSON 契约 → 邮箱/命令）。
