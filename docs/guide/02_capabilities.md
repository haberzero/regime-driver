# 你能做什么：能力一览

> 本篇按"你能达成什么目标"组织，不按命令/参数组织。所有操作都可以通过上帝对话框对话完成；
> 底层命令只在你想手动操作时用（细节见"查询参考"）。

## 一、用对话完成任务

- **启动一个任务**：说"跑 code_workflow 实现某某功能"，对话框启动并跟踪。
- **看任务进度**：随时问"现在跑到哪了"、查看事件。
- **和某个工作会话对话**：直接和一个 opencode session 单独交流（`talk`）。

> 为什么这么设计：你关心的是"任务完成了没有"，而不是"哪个节点在哪个 session 上"。
> 对话框把后者替你处理了。

## 二、官方工作流程模板：制度驱动规划的样板

为了理解"你的编程指令如何被制度化地执行"，先看官方自带的流程模板 `code_workflow`。
它不是"一个 agent 自由发挥"，而是一条**结构化的制度路径**：

| 节点 | 角色 | 类型 | 技能 | 职责 |
|---|---|---|---|---|
| understand | developer | agent | — | 理解任务上下文 |
| read_code | developer | agent | — | 理解代码上下文 |
| design | reviewer | judge | design-philosophy | 按设计哲学审查方案 |
| implement | developer | agent | — | 实现 |
| test | reviewer | judge | code-review | 按代码审查规则检查实现 |
| wrap | developer | agent | — | 收尾 |

**这条模板说明了核心机制**：

- **你的指令是目标，不是命令**。当你说"用 code_workflow 实现某某"，系统不会把你的话原样丢给
  一个 agent，而是：结合你的需求（任务上下文）、结合这条流程的全部信息（各节点/角色/技能）、
  结合 regime-driver 的可用能力（驱动/监督/审查/报告），**从制度驱动的角度规划如何实现**——
  选定流程 → 编译成状态机 → 按节点驱动。
- **干活与审查分离**。developer 负责 understand/read_code/implement/wrap（做事），
  reviewer 负责 design/test（判定）。审查不过关，流程**不前进**。
- **技能按节点注入**。design 节点注入 `design-philosophy`，test 节点注入 `code-review`——
  给审查角色它恰好需要的规则，不常驻、不稀释。
- **全程记录**。每一步（节点进入/完成/审查判定/流转/最终结果）都写入报告与事件账本，可复盘。

> 为什么这么设计：制度驱动意味着"流程是结构，不是建议"。你的指令接上制度后，
> 每一步谁做、按什么规则做、做完怎么验证，都是确定的——这正是"元指令不会遗忘"的保证。

## 三、用对话设计流程

- **用自然语言设计流程**：说"设计一个先实现、再审查、再测试的流程"，对话框编译并注册。
- **查看已注册流程**：列出所有可运行的流程（`flow list`）。
- **让对话框代写流程 JSON**：你不必手写 JSON——描述意图即可。

> 为什么这么设计：流程是体系的心脏，但"怎么写流程文件"是技术细节。对话框把它变成一句话的事。

## 四、监控与复盘

- **全局态势**：一句话看 worker 健康、运行中的任务、会话情况（`status` / `sessions`）。
- **事件回看**：看最近发生了什么（`watch` / `events`）。
- **报告看板**：把多次运行汇总成可读报告（`report`）。

> 为什么这么设计：系统会自动记录每一次运行（报告日志 + 事件账本），你能复盘"当时为什么这样走"。

## 五、监督与恢复（自动）

- **进程外监督**：系统自带一个独立监督器，周期性检查 worker 健康、任务是否停滞、有没有超时。
- **自动纠正**：发现问题按既定阶梯处理（提示/中止/换模型/重启），不需要你盯着。

> 为什么这么设计：卡死/打转是 agent 工作的常见问题。让独立的时钟盯着，而不是靠人。

## 六、并发与隔离

- **多任务并行**：同时跑多个任务，互不干扰（`run-many`）。
- **工作区隔离**：每个任务在独立的 worker 实例里跑，产物互不污染（`drive --workspace` / 舰队）。

> 为什么这么设计：真实使用中会有多个任务。物理隔离保证它们不互相踩踏。

## 七、健康与自检

- **一键自检**：`doctor` 检查 worker 健康、模型密钥、官方模板是否就绪。
- **配置就绪**：`regime scaffold` 一条命令部署官方模板，`doctor` 验证。

> 为什么这么设计：减少"配置半天才发现某个环节错了"的挫败感。

## 八、资源治理

- **自动清理会话**：长期运行后，可用一句话让系统清理累积的会话（`sessions --cleanup`）。
- **报告保留**：journal 可设保留策略，防止无限增长。

> 为什么这么设计：长期运行会累积会话记录；治理工具让你不必手动清理。
