# 教程 00-0 · 心智模型（先读这一篇）

> 面向第一次接触 regime-driver 的外部读者。本文解释"它解决什么问题、怎么工作的",
> 不涉及任何命令细节。读完你应能回答：它是什么？和我直接跑一个 opencode agent
> 有什么不同？为什么要这一整套？

## 一句话

**regime-driver 是一个"流程执行器"**：它把你定义好的**制度化流程**（一份 JSON 状态机）
编译成可执行流程，然后在一个干净、无插件的 opencode worker 上**逐节点驱动**它完成真实任务，
并由一个**进程外的监督器**（独立时钟）在旁看护——发现停滞/卡死/超时就用既定阶梯纠正。

## 它解决什么问题（为什么不用裸 agent）

| 裸 opencode agent | regime-driver |
|---|---|
| 你给一句任务，agent 自由发挥 | 你给一份**流程**，每个节点是明确的一步（理解→设计→实现→测试→收尾） |
| 没有强制审查 | 流程里可插入 **judge 节点**（只读审查者判定），过不了确定性门就不前进 |
| 卡死/打转靠人盯着 | 进程外 **supervisor**（独立时钟）检测停滞，自动 abort/回退/重启 |
| 无法复盘"当时为什么这样走" | 全程写 **report journal + event ledger**，可回放、可报告 |
| 无法批量/并发隔离 | 支持 **fleet / 多工作区**（每任务一个隔离 worker 实例） |

核心差异一句话：**你从"让一个 agent 干活"变成"让一个流程机制替我管理 agent 干活"**。

## 三层心智模型

```
你（人类 / 上帝对话框）          ← 控制面：regime dialog、regime drive、CLI
        │ 定义流程 / 下达任务 / 监控
        ▼
regime-driver（元层）            ← 状态机 + supervisor + reporter（本仓库）
        │ 按流程逐节点驱动 / 监督 / 记录
        ▼
opencode worker（执行层）        ← 干净无插件的 opencode 服务（容器），只干活不自治
```

- **执行层**：一个普通 opencode 服务，不含任何制度/流程逻辑——它只按收到的指令干活。
- **元层**（本仓库的核心）：把"制度"（流程定义、审查纪律、监督策略）做成确定性的软件，
  而不是又一个 agent——因为 agent 守不住固定流程，**固定流程必须用确定性脚本硬约束**。
- **控制面**：你通过 CLI 或上帝对话框与元层交互。

## 两个"时钟"为什么重要

裸 agent 自己不会发现"自己卡死了"。所以系统里有两个独立时钟：

1. **工作流线程**：驱动流程前进（每次给节点发指令、等结果、判 verdict）。
2. **进程外 supervisor**：独立于工作流存在，周期性看护 worker 健康、会话停滞、全局期限。

因为 supervisor 不在工作流内部，它能在工作流"卡死/思考死循环"时仍然清醒地介入。
这就是"元层必须有独立时钟"的设计根因（也是本仓库历史踩坑的核心教训）。

## 确定性 vs 智能的分工

- **确定性**（代码保证）：流程结构、审查门禁、停滞检测、权限门禁、报告归档。
- **智能**（模型参与）：节点内干活、judge 判定、supervisor 的元分析（可选）。

系统原则：**该确定的地方绝不让模型自由发挥**（流程、门禁、监控），模型只在其该干的地方干活。

## 你现在应该明白

- 它是什么：把制度化流程编译成状态机、在干净 worker 上驱动并监督的"流程执行器"。
- 和裸 agent 的区别：多了流程约束、强制审查、独立监督、全程可复盘。
- 三层的职责：执行层干活、元层管制度、控制面管交互。
- 两个时钟：工作流推进 + 进程外监督。
