# regime-driver 技术文档书写准则

> 本文档是本仓库**全部技术文档的强制书写准则**。对象为输入/修改 `docs/` 目录下技术文档的写作者。
> 按写作者的决策流程组织：先定归属，再搭骨架，再写段落，再套格式，最后验收。
> 任何新增或修改技术文档内容时，对照本文件自查。
>
> **适用范围**：`docs/` 下全部技术文档——根索引手册（`README.md`、`CLI_REFERENCE.md`、
> `ARCHITECTURE.md`、`SUBSYSTEM_DESIGN.md`、`KNOWN_LIMITS.md`）与各子目录（`guide/`、`howto/`、
> `reference/`、`architecture/`、`subsystems/`）。
> 任务/过程文档（根 `AGENTS.md`、`TASK.md`、`WORK_PLAN*.md`、`HANDOVER.md`）不在本准则管辖范围内，
> 属智能体工作流层。`tasks_docs/` 若存在亦不受本准则约束（历史档案区）。

---

## A. 体系设计：写之前先定归属

### A.1 文档的唯一目的

技术文档的唯一目的：**让读者在不依赖作者的情况下，独立建立对系统的心智模型，并能基于该模型做出正确决策。** 文档不是工作日志，不是代码的散文翻译，也不是决策过程的会议记录。

### A.2 动笔前三问

读者是谁？读完后要能做什么？当前不知道什么（文档只填补这个缺口）？

### A.3 文档按读者旅程分层（Divio 体系）

本仓库文档体系遵循 Divio 四分法，并映射到本仓库的组织方式（见 `docs/README.md`）。每篇文档应明确自身属于哪一类，并使用对应的写作风格：

| 类型 | 本仓库载体 | 写作要求 |
|------|-----------|----------|
| **教程（Tutorial）** | `guide/` | 面向初学者，按步骤引导，每步结果可预期，允许省略细节 |
| **操作指南（How-to）** | `howto/` | 面向有基础的用户，解决具体问题，以问题为标题，列出步骤 |
| **参考（Reference）** | `reference/` | 信息完备，描述精确，每个章节独立可读，不解释为什么 |
| **解释（Explanation）** | `architecture/`（原则与全貌）、`subsystems/`（模块实现） | 面向理解，阐述设计理由与背景，提供概念框架 |

同一篇文档不得同时充当两种角色。例如，在参考（CLI 契约）中穿插设计理由叙述会干扰读者定位。

### A.4 概念归属唯一

每个概念有且仅有一个文档拥有其完整解释。其他文档引用它，不复制它。部分复制必然漂移——两处描述同一事物，改一处忘另一处，读者不知哪处为真。

### A.5 体系是设计出来的

新增文档前必须回答：这个概念的归属文档是谁？归属文档已存在则扩展它；必须新建则明确它在体系中的位置。应显式设计文档体系的结构（哪些文件存在、各自覆盖什么、如何组合为整体）。

### A.6 文件身份完整性

标题、定位段、实际内容三者必须一致。文件名承诺什么，内容就必须交付什么。新增内容若不匹配文件已声明的范围，放入正确的归属文件，而非追加到当前文件。

### A.7 层间正交

参考手册回答"怎么用"，架构文档回答"为什么这样"，子系统文档回答"内部怎么实现"。同一事实不在两层重复描述。抽象粒度递进：

| 层级 | 允许出现 | 不允许出现 |
|------|---------|-----------|
| `reference/` | 用户可见命令、配置字段、契约、行为 | 内部实现模块路径 |
| `architecture/` | 架构概念、设计理由、组件关系 | 逐行代码解释 |
| `subsystems/` | 实现细节、模块交互、数据流、代码路径 | 使用说明（属于 reference/） |

### A.8 信息架构：读者旅程

文档按读者旅程组织，而非按代码文件组织。一个读者解决一个典型问题需要跨越哪些文档？这些文档之间如何引导？

每个文档的定位段应明确读者需要的前置知识，并在末尾的"深入指引"中给出下一步阅读方向。跨文档的引用链形成多个"读者旅程线"——例如：

> 新用户旅程：根 `README.md` → `docs/README.md`（导航）→ `guide/`（教程）→ `reference/`（查契约）→ `KNOWN_LIMITS.md`（查边界）
> 开发者旅程：`docs/README.md` → `ARCHITECTURE.md`（全貌）→ `architecture/`（原则）→ `subsystems/`（模块）→ 源码

## B. 文档结构：骨架

### B.1 单篇文档骨架

```
标题（精确描述覆盖范围的名词短语）
├── 定位段（1-3句：本文是什么、给谁看、覆盖什么）
├── 核心概念（读者必须建立的心智模型）
├── 主体内容（按读者认知顺序，非按代码文件顺序）
├── 约束与限制（读者必须知道的边界）
└── 深入指引（可选：指向更细节的文档，非必须阅读）
```

**示例——合格的定位段**：

> 本文档描述 regime-driver 的状态机执行规范，包括并发运行时、宪法信号协议与根不变量。
> 面向需要实现或验证 regime 运行时的开发者。阅读前需了解流程状态机（见 `core/state_machine.py`）。

**示例——不合格的定位段**：

> 本文档是关于运行时的。（❌ 未说明覆盖范围、读者对象、前置知识）

### B.2 渐进披露（倒金字塔）

最重要的信息在最前面。读者可能只读第一段就离开——第一段必须传达核心。读者可能只读标题就停止——每个标题本身必须是信息性的。如果一个读者只有 30 秒，他至少应能获取本文的核心不变量。

**示例——信息性标题**：

> ### 2.3 宪法 STOP 的触发条件（✓ 标题即答案）
> ### 2.3 关于宪法的一些说明（✗ 标题不包含信息）

### B.3 章节是论证链的环节

每章回答一个明确的问题，章节间存在逻辑推进关系（递进 / 并列 / 总分 / 对比）。章节标题是名词短语（回答"什么"），不是动词短语（"实现X"）。不按代码文件顺序排列。

**示例——合格与不合格的章节标题**：

> ### 三、工作流热重载的原子性（✓ 名词短语，回答"什么"）
> ### 三、实现工作流热重载（✗ 动词短语，回答"怎么做"）

### B.4 信息密度有节奏

章节开头低密度（建立方向）→ 核心论述高密度（规则、表格）→ 示例中密度（呼吸空间）→ 边界中低密度。全文高密度无喘息是反模式；全文低密度（水）也是。

## C. 段落与行文：肌肉

### C.1 段落是最小论证单元

段落不是"几句话的集合"。三要素：

1. **主题句**（第一句）：声明本段要建立的一个事实。仅读此句即可获取核心信息。
2. **支撑**（中间）：解释机制、给出约束、提供示例。不引入新论点。
3. **收束**（可选末句）：点明边界、例外、或引出下一段的问题。

**检验**：遮住中间和末尾，仅读第一句——若无法判断"这段在讲什么"，主题句不合格。

**示例——合格段落**：

> 宪法以运行时强制的根不变量实现自我监管。每个运行期都必须存在至少一个 watchdog 单元（I1），
> STOP 通道不可被工作单元关闭（I2），元迭代次数有上界（I3）。这些不变量在 `Runtime.start`
> 时校验，违反即拒绝启动。这保证任何用户自定义宪法都无法移除系统的紧急停止能力。

**示例——不合格段落**：

> 宪法是一个很重要的概念。我们之前讨论过它的实现方式。目前它是通过根不变量实现的，这意味着运行时
> 会检查这些不变量。之前我们考虑过别的方案，但后来发现有问题，所以改成了现在这样。（❌ 主题句不明确，含历史叙述，未收束）

### C.2 行文四规则

| 规则 | 说明 |
|------|------|
| 陈述式，非探索式 | 陈述已确定的事实，不记录探索过程 |
| 现在时态，非历史时态 | 描述当前状态，不描述演变。变更历史属于 git |
| 主动语态，明确主语 | "宪法广播 STOP"而非"STOP 会被广播" |
| 精确且完备 | 精确 = 读者能据此判断自己的配置是否合规；完备 = 不存在需要猜测的隐含条件 |

### C.3 术语管理

首次出现时**用粗体标注**一句话定义，后续不重复。一词一义，一义一词。代码标识符（`WorkflowUnit`）与散文术语（"工作流单元"）对应但不混用。

### C.4 设计理由的书写

遵循"约束 → 决策 → 后果"三段式：因为 [不可改变的外部条件]，系统选择 [具体方案]，这意味着 [读者需要知道的行为影响]。

不写探索过程（"试了A不行又试了B"），不写无约束的决策（"使用状态机"——为什么？），不写无后果的约束（"因为性能"——所以对我有什么影响？）。

**示例**：

> 因为 AI 模型调用的 HTTP 往返延迟远大于本地计算，系统选择把超时判定放在进程外的 supervisor（独立时钟），
> 而非依赖 worker 内的监控线程。这意味着即使 worker 完全卡死，supervisor 仍能检测并重启，而不会与
> 被监督的进程同归于尽。

### C.5 表格 vs 散文

多个对象具有相同属性维度（平行对比）→ 表格。单个概念的因果链解释 → 散文。信息是枚举性的 → 表格。信息是推导性的 → 散文。表格列数不超过 5。

### C.6 示例设计

- **最小充分**：只含说明当前论点所需的最少元素
- **配对出现**：正面 + 反面
- **注释说明意图**（"为什么选择这种写法"），不解释代码做了什么
- **排列顺序**：规则反直觉时先示例后规则（归纳）；规则自然时先规则后示例（演绎）

**示例——正面与反面配对（regime 配置）**：

```toml
# ✅ 正确：默认模型走官方 API（env 注入 key，不入库）
model = "deepseek-api/deepseek-v4-flash"
```

```toml
# ❌ 错误：在仓库可提交配置里写死真实 key，会泄露凭据
model = "deepseek-api/deepseek-v4-flash"
# api_key = "sk-xxxxx"   # ← 绝不写真实 key
```

### C.7 可读性约束

| 维度 | 约束 |
|------|------|
| 句子 | 单句不超过 40 字（中文）。超过则拆分 |
| 段落 | 不超过 8 句。超过则检查是否混入第二个论点 |
| 嵌套 | 列表嵌套不超过 3 层。超过则拆为独立小节 |
| 代码块 | 文档中代码片段不超过 20 行。超过则考虑引用源文件 |
| 表格 | 列数不超过 5。超过则拆分或改用散文 |
| 单篇长度 | 超过 500 行时审视是否应拆分 |

## D. 条目格式模板：骨骼

技术手册中大量出现"平行小节"，每个小节对一个特定的 API、类型、协议或模块作说明。这些平行小节必须遵循**严格一致的格式模板**，使读者建立阅读预期后能快速定位信息。

### D.1 五种模板

**命令/CLI**：签名（子命令 + 参数）→ 一句话职责 → 参数表 → 输出/返回语义 → 约束/权限（如有）→ 示例。

**配置字段**：一句话定位 → 类型/默认值 → 语义 → 约束（如有）→ 示例。

**数据类型/规格**：一句话定位 → 结构 → 字段表 → 核心不变量（2-5条）→ 与其他机制的交互（如有）→ 示例。

**协议/机制**：一句话职责 → 触发时机 → 契约（保证什么 / 依赖什么）→ 默认行为（如有）→ 示例。

**技术模块/子系统**：一句话定位 → 职责边界（做什么/不做什么）→ 对外接口表 → 内部结构（如需）→ 与其他模块的关系 → 约束。

### D.2 一致性原则

同一文档内所有平行小节必须使用同一模板。槽位要么填写要么整行省略，不得留空或写"无"。一句话说明必须是完整陈述句。表格列数在同一文档内保持一致。

### D.3 模板骨架速查

```
命令/CLI                         配置字段
─────────────────────────        ─────────────────────────
### `子命令`                     ### `字段名`
一句话职责。                     一句话定位。
**参数**：| 参数 | 类型 | 说明 |   **类型/默认**：类型（默认值）。
**输出**：返回语义。              **语义**：说明。
**权限**：（如有）               **约束**：（如有）
**示例**：                      **示例**：
```

## E. 红线：禁止书写的内容

| 禁止 | 原因 |
|------|------|
| 过程叙述（"经过讨论/验证/实测..."） | 读者只需结论 |
| 历史演变（"旧X已删除，现为Y"） | 属于 git 历史 |
| 日期戳 / 完成标记（"已解决"、"已落地"、"最后更新：..."） | 文档正确则不需时间证明；不正确则时间不能拯救 |
| 未实现的设计（除非独立"规划"章节且明确标注） | 文档描述当前真实行为 |
| 自治豁免标注（"已归档"、"封存"、"备份，不参与治理"） | docs/ 一律受本准则约束；归档/备份内容移入 `tasks_docs/`，未完成规划进任务控制文档 |
| 任务编号 / 里程碑代号 / PR 编号 | 对读者是噪音 |
| 冻结的测试通过数字（"N passed"） | 数字纪律：测试基线只在 `TASK.md` 顶部写一次，其余文档用"以 `python -m pytest` 实跑为准" |
| 代码的散文翻译（逐行解释代码做了什么） | 代码自己会说 |
| 核查记录 / 验证清单 / 进度表 / 状态追踪 | 过程产物，属于 git 或任务文档 |
| 只有作者能理解的缩写/代号 | 用描述性名称替代 |
| 混合抽象层级（用户命令和内部模块路径同段出现） | 读者无法确定自己在哪个层级思考 |
| 过时信息 | 比没有信息更危险 |
| 未标注的假设 | 读者无法判断自己是否具备理解条件 |

## F. 引用与代码片段：工具

### F.1 引用

引用是补充，不是替代。删掉引用后当前段落必须仍然可理解。若删掉后信息量归零，说明当前文档缺少自己的叙述——修复方式是补全叙述，而非保留引用。

引用的正确用途："本机制的完整形式化定义见 X"（当前已给出足够理解的摘要）。不用行号（用模块路径+类/函数名、章节名、或概念名）。不引用已删除/重组的路径。跨文档引用统一使用**仓库相对路径**，Markdown 超链接用**相对于本文件**的路径，迁移文件时必须同步修正。FAQ 必须附着于其所澄清的文档。

### F.2 代码片段

代码片段三条件（必须同时满足）：
- 有上下文说明（在做什么、为什么出现）
- 自包含（不需打开源文件即可理解）
- 必要（自然语言无法同等精确表达）

做不到则删除，改用自然语言。

### F.3 代码注释与文档的边界

对"正在修改这行代码的人"有用的信息是注释（局部设计意图、已知陷阱、不变量声明）。对"使用这个系统的人"或"理解这个设计的人"有用的信息是文档（完整机制、概念模型、使用指南）。

## G. 质量检验：验收

### G.1 段落级

遮住段落中间和末尾，仅读第一句——能否判断"这段在讲什么"？

### G.2 文档级（5 分钟测试）

一个具备基本背景知识的新读者，花 5 分钟阅读本文后，能否：
1. 说出本文覆盖什么、不覆盖什么
2. 说出核心不变量（1-3 条）
3. 知道在哪里找到更细节的信息
4. 不会基于本文做出错误的使用决策

任何一条不满足则文档不合格。

### G.3 体系级

本文描述的概念，其归属文档是否是本文？是否存在另一处部分复制了同一内容？删掉所有引用后本文是否仍然自包含？

### G.4 文档健康检查清单

新增或重大修改文档后，逐项通过：

- [ ] 有定位段（1-3句：本文是什么、给谁看、覆盖什么）
- [ ] 标题是名词短语，精确描述覆盖范围
- [ ] 定位段、标题、实际内容三者一致（§A.6）
- [ ] 无日期戳、无"最后更新"、无"已解决"标记
- [ ] 无历史叙述（"原实现采用..."、"经过讨论..."）
- [ ] 无自治豁免标注（"已归档"/"封存"/"备份，不参与治理"）
- [ ] 无任务编号、里程碑代号、PR 编号
- [ ] 无冻结的测试通过数字
- [ ] 无代码的散文翻译
- [ ] 段落不超过 8 句，单句不超过 40 字（中文）
- [ ] 代码片段不超过 20 行
- [ ] 文件不超过 500 行（超过则审视是否应拆分）
- [ ] 表格列数不超过 5
- [ ] 5 分钟测试通过（§G.2）
- [ ] 无跨层抽象混用（§A.7）
- [ ] 平行小节格式一致（§D.2）

## H. 文档评审流程

新增或重大修改的文档需经过以下评审：

1. **自检**：走完 §G.4 健康检查清单，逐项勾选
2. **同行评审**：一个非作者读者花 5 分钟阅读后，能否正确回答 §G.2 的四个问题
3. **一致性检查**：确认新增/修改内容不与已有文档的描述冲突（§A.4 概念归属唯一）
4. **链接检查**：确认所有跨文档引用路径有效，不存在指向已删除文件的链接
